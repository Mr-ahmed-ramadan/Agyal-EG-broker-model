# ADR 0003: FIX-Native Order Model

## Status

Accepted

## Context

The platform must be built on the FIX protocol natively, not as a proprietary
API with a FIX bridge added later. Fixed income in Egypt is traded OTC
through banks, so the core interaction is a **request for quote (RFQ)**
followed by an order against the chosen quote.

"FIX-native" can mean three things:

1. **Outbound**: the platform talks FIX to execution counterparties (banks).
2. **Internal model**: the platform's own order/quote/execution data and
   state machine *are* FIX semantics (message types, `OrdStatus`, `ExecType`,
   standard tags), whatever transport a counterparty uses.
3. **Inbound**: brokers' own systems (back office, equity OMS) connect to the
   platform over FIX, e.g. to receive a drop copy of trades.

## Decision

**Adopt (1) and (2) in Phase 1; design for (3) and defer it.**

### Internal model = FIX semantics

- The domain entities map 1:1 to FIX messages and use FIX field names and
  enumerations as their canonical values:

  | Entity | FIX message(s) |
  | --- | --- |
  | `QuoteRequest` | `QuoteRequest <R>`, `QuoteRequestReject <AG>` |
  | `Quote` | `Quote <S>`, `QuoteCancel <Z>`, `QuoteResponse <AJ>` |
  | `Order` | `NewOrderSingle <D>`, `OrderCancelRequest <F>`, `OrderCancelReject <9>` |
  | `Execution` | `ExecutionReport <8>` (append-only) |
  | `TradeConfirmation` | `Confirmation <AK>` / `TradeCaptureReport <AE>` where the bank supports it |

- `Order.ordStatus` and `Execution.execType` use the FIX code values
  (`OrdStatus(39)`: `A` PendingNew, `0` New, `1` PartiallyFilled, `2` Filled,
  `4` Canceled, `6` PendingCancel, `8` Rejected, `C` Expired). The order state
  machine is the FIX one; transitions are only driven by `ExecutionReport`s
  (real ones from a FIX bank, or synthesised by the non-FIX adapters in
  ADR 0004).
- Identifiers follow FIX rules: `ClOrdID(11)` is generated by the platform and
  unique per bank session; `OrderID(37)` and `ExecID(17)` come from the bank;
  `QuoteReqID(131)` and `QuoteID(117)` link quotes to orders.
- Fixed-income fields are first-class: `SecurityID(48)` +
  `SecurityIDSource(22)=4` (ISIN), `Side(54)`, `OrderQty(38)` (face/nominal),
  `PriceType(423)` (`1` percentage of par or `9` yield), `Price(44)`,
  `Yield(236)`, `AccruedInterestAmt(159)`, `SettlDate(64)`,
  `GrossTradeAmt(381)`, `NetMoney(118)`.
- Client/broker identification uses the `Parties` repeating group
  (`NoPartyIDs(453)`): executing firm (broker), client account, and the
  client's MCDR unified code, so the bank can book to the right custody
  account without side channels. The exact party roles are agreed per bank
  in its rules of engagement.

### Order flow (Phase 1, one order per client)

```
Client          Platform (API)            FIX Gateway            Bank(s)
  | request price  |                           |                      |
  |--------------->| QuoteRequest (R) x N banks|--------------------->|
  |                |<--------------------------| Quote (S)            |
  |  best quote    | apply broker markup (0008)|                      |
  |<---------------|                           |                      |
  | accept         | pre-trade checks:         |                      |
  |--------------->|  KYC active, unified code,|                      |
  |                |  suitability, cash, limits|                      |
  |                | [optional broker dealer   |                      |
  |                |  release, per tenant]     |                      |
  |                | NewOrderSingle (D)        |                      |
  |                |  OrdType=D (prev. quoted) |--------------------->|
  |                |<--------------------------| ExecutionReport (8)  |
  |  confirmation  | ledger postings (0007)    |  New -> Filled       |
  |<---------------|                           |                      |
```

- Quotes are firm for a bank-specified time (`ValidUntilTime(62)`); the
  client sees a countdown and the order is rejected by the platform if it
  expires before release.
- Primary T-bill auction subscriptions do not fit RFQ; they are modelled as a
  `NewOrderSingle` to the bank with `OrdType=2` (limit, yield bid) or
  non-competitive, with the bank reporting the allotment via
  `ExecutionReport`. The exact flow per bank is an open question.

### Message store and audit

- Every FIX message in and out is persisted raw (tag=value) with sequence
  numbers, session ID and timestamps, in an append-only store, plus the
  parsed domain record. This is both the FIX session store (for resends) and
  the regulatory audit trail.
- Nothing about an order is ever updated in place except its current-state
  projection; history is the sequence of `Execution` rows.

### Inbound FIX (deferred)

- The same entities are exposed later through a FIX **acceptor** per broker:
  drop copy of `ExecutionReport`s first, order entry later. Because the
  internal model is already FIX, this is mapping, not redesign.

## Consequences

- Developers need working FIX knowledge; a FIX primer and the per-bank rules
  of engagement live in `docs/fix/`.
- Banks without FIX are handled by adapters that produce the same messages
  (ADR 0004), so the core never has a second, non-FIX order path.
- FIX 4.4 is the default dictionary (the version most banks' fixed-income
  desks support); a bank on FIX 5.0 SP2 / FIXT 1.1 is a per-session config
  change in the gateway.
